8.1What does the Transport layer do?

The Network layer gets data from one host to another. The Transport layer gets it to the right process/application. IP gets the packet to Google's server; the port number gets it to the web server process.

8.4TCP segment and UDP datagram headers

Most important TCP fields: Sequence Number, Acknowledgement Number, Flags, Window Size.

+ Added · header details
  • Seq and ACK numbers are 32-bit; they wrap around (2³² bytes ≈ 4 GB).
  • Data offset = header length in 4-byte words (5–15 → 20–60 bytes).
  • Window is 16-bit (max 65,535 bytes); the window scale option multiplies it (up to 2¹⁴×) for fast links.
  • Common options: MSS, window scale, SACK-permitted, timestamps.
  • MSS (Maximum Segment Size) = MTU − IP header − TCP header = 1500 − 20 − 20 = 1460 bytes on Ethernet.
  • Flags: URG, ACK, PSH, RST, SYN, FIN (+ ECE, CWR for ECN).
  • UDP checksum is optional in IPv4 but mandatory in IPv6.

UDP header size: 8 bytes (source port, destination port, length, checksum). TCP minimum header: 20 bytes.

Multiplexing (sender): Chrome, Spotify and Discord all send at once; the Transport layer combines their data and tags each with port numbers. Demultiplexing (receiver): Transport reads the destination port (e.g. 443) and hands the data to the correct process. + Added UDP demultiplexes by (dst IP, dst port) only; TCP uses the full 4-tuple, which is why each TCP connection gets its own socket.

One of the most frequently asked CN topics. Don't just memorise SYN → SYN-ACK → ACK; understand why each step exists.

9.1Why does TCP need a handshake?

TCP is connection-oriented. Before sending data, both sides must agree on state, especially:

  • Each side's Initial Sequence Number (ISN)
  • Connection state (and options like MSS, window scale, SACK)
  • Proof that both directions work

+ Added The third ACK may already carry data. The ISN is chosen randomly (not 0) so old segments from a previous connection and blind spoofing attacks are unlikely to match.

9.3Why 3-way and not 2-way?

Both sides need to know the other can send and receive, and sequence numbers must be synchronised in both directions.

  • After SYN → SYN-ACK, the client knows the server got its SYN and can reply.
  • But the server doesn't yet know the client received the SYN-ACK (and so the server's ISN y).
  • The third ACK confirms that.

+ Added It also protects against old duplicate SYNs: if a delayed SYN from a dead connection arrives, the server's SYN-ACK gets a RST from the client instead of opening a ghost connection, which a 2-way handshake could not prevent.

9.4Sequence numbers and ACK numbers

TCP is a byte-stream protocol: sequence numbers count bytes, not segments.

ISN = 1000, send 500 bytes → they occupy 1000 to 1499 → receiver replies ACK = 1500 ("I've got everything before 1500, send 1500 next"). The next segment carries Seq = 1500.

RulesACK number = next byte expectedNext Seq = Seq + data lengthSYN consumes 1 sequence numberFIN consumes 1 sequence numberA pure ACK (no data) consumes 0

Classic trap: client SYN with Seq = 100 → server replies Ack = 101 (the SYN consumed one number).

What if a segment is lost?

Sender sends 1000–1099, 1100–1199 (lost), 1200–1299. Receiver got the first and third, but still expects 1100, so it keeps sending ACK = 1100. These are duplicate ACKs. Three of them trigger Fast Retransmit (Congestion Control chapter).

9.6SYN flood attack

The attacker sends lots of SYNs (often from spoofed IPs). The server replies SYN-ACK and keeps state for each half-open connection in its backlog queue, but the final ACK never comes. The queue fills and real clients can't connect: a denial of service.

+ Added Defences: SYN cookies (encode the connection state into the server's ISN so no memory is kept until the ACK returns), larger backlog, shorter SYN-RECEIVED timeouts, rate limiting, upstream DDoS scrubbing.

Connects sequence numbers, ACKs, retransmission, receiver window and sliding window. The foundation for congestion control.

10.1Why a sliding window?

Stop-and-Wait: send one segment, wait for its ACK, send the next. Reliable but slow, especially when delay is large: the link sits idle for a whole RTT after every packet. A sliding window lets multiple bytes/segments be in flight before waiting for ACKs, which improves utilisation.

How much better? + AddedStop-and-Wait efficiency η = 1 / (1 + 2a),  a = Tp / TtWindow of N: η = min(1, N / (1 + 2a))Window needed for 100% utilisation: N ≥ 1 + 2a

Example: Tt = 1 ms, Tp = 10 ms → a = 10 → Stop-and-Wait η = 1/21 ≈ 4.8%. A window of 21 fills the pipe.

TCP's window is measured in bytes, not packets. Below, the window covers what may be sent without waiting; it slides right as ACKs come in.

Why "sliding"? Suppose the window initially covers four positions. As the receiver acknowledges the first part, the window moves forward:

[1000 1010 1020 1030]
      [1010 1020 1030 1040]     ← first part ACKed
            [1020 1030 1040 1050]

The window slides forward as data is acknowledged. Byte view: if the current window allows 1000 → 1399, the sender may send all of those bytes without waiting for further ACKs.

10.2Flow control and rwnd

The sender can transmit much faster than the receiver's application reads. If it sends too much, the receive buffer overflows and data is lost. Flow control prevents the sender from overwhelming the receiver.

The receiver advertises a Receive Window (rwnd) in every segment: "you may have up to rwnd more bytes outstanding". If rwnd = 5000, the sender must keep unacknowledged data ≤ 5000.

The one formulaEffective send window = min(rwnd, cwnd)

rwnd protects the receiver; cwnd protects the network. Example: rwnd = 10 KB, cwnd = 6 KB → 6 KB (network limits). Later rwnd = 4 KB, cwnd = 6 KB → 4 KB (receiver limits).

+ Added · edge cases interviewers like
  • Zero window: receiver advertises rwnd = 0, sender stops and runs a persist timer, sending small window probes so a lost "window open" update can't deadlock the connection.
  • Silly Window Syndrome: tiny windows cause tiny segments (40 B header for 1 B data). Fixes: receiver waits until it can advertise a decent window (Clark); sender uses Nagle's algorithm (buffer small writes while an ACK is outstanding).
  • Delayed ACK: receiver waits up to ~200 ms (or every 2nd segment) to ACK. Nagle + delayed ACK together can add latency; interactive apps set TCP_NODELAY.

10.3Cumulative ACKs, loss and retransmission

TCP commonly uses cumulative ACKs: receiving 1000–1099, 1100–1199, 1200–1299 → one ACK = 1300 confirms everything before 1300.

If 1100–1199 is lost, the receiver keeps sending ACK = 1100 for every later segment: duplicate ACKs.

Loss signal 1: Timeout

No ACK before the retransmission timer (RTO) expires → retransmit. Strong congestion signal.

Loss signal 2: Duplicate ACKs

3 duplicate ACKs → fast retransmit without waiting for the timer.

How long is the timeout? + Added

RTO estimation (Jacobson / RFC 6298) EstimatedRTT = (1 − α)·EstimatedRTT + α·SampleRTT  α = 1/8 DevRTT = (1 − β)·DevRTT + β·|SampleRTT − EstimatedRTT|  β = 1/4 RTO = EstimatedRTT + 4·DevRTT

Karn's algorithm: don't take RTT samples from retransmitted segments (you can't tell which copy was ACKed), and double the RTO after each timeout (exponential backoff).

TCP nuance

Don't blindly say "TCP = Selective Repeat". Classic TCP uses cumulative ACKs and its retransmission behaviour resembles Go-Back-N in some respects, but receivers buffer out-of-order data, and modern TCP uses SACK (Selective Acknowledgment) so the receiver can say "I'm missing 3, but I have 4 and 5", and only the gap is resent. The main question: how much data should a TCP sender put into the network without causing congestion? One of the most algorithm-heavy placement topics.

11.1cwnd and ssthresh

Flow control

Protects the RECEIVER → rwnd

Congestion control

Protects the NETWORK → cwnd

cwnd (congestion window) is kept by the sender only (never sent in a header). It limits how much unacknowledged data can be in the network: cwnd = 10 KB → ~10 KB in flight, subject to rwnd.

ssthresh (slow start threshold) decides when TCP switches from Slow Start to Congestion Avoidance.

TCP has no explicit signal from routers (unless ECN), so it infers congestion from loss: a timeout or duplicate ACKs.

11.2See it: the cwnd graph

Pick ssthresh and when the losses happen. The chart draws Tahoe and Reno together so the difference is obvious. Hover or tap a point for the round's value.

11.3Slow Start

Despite the name, Slow Start grows very quickly. It starts small because the sender doesn't know the network's capacity, then increases while watching for trouble.

cwnd grows by 1 MSS for every ACK received, which doubles cwnd every RTT: 1 → 2 → 4 → 8 → 16 → 32 MSS. Exponential growth.

When cwnd ≥ ssthresh, TCP enters Congestion Avoidance. + Added Modern stacks start with an initial window of 10 MSS (RFC 6928), not 1.

11.4Congestion Avoidance and AIMD

Growth becomes roughly linear: about +1 MSS per RTT (16 → 17 → 18 → 19 → 20). This follows AIMD:

  • Additive Increase: no trouble → cwnd += ~1 MSS per RTT.
  • Multiplicative Decrease: congestion detected → cwnd ≈ cwnd / 2 (e.g. 20 → 10).

Repeated, this gives the famous sawtooth. + Added AIMD is used because it converges to fairness: competing flows end up sharing the bottleneck roughly equally.

11.5Fast Retransmit and Fast Recovery

Packet 3 is lost while 4 and 5 arrive; the receiver keeps ACKing the gap, so the sender sees duplicate ACKs. After 3 duplicate ACKs, TCP performs Fast Retransmit: resend the missing segment immediately, without waiting for the timeout.

3 dup ACKs mean data is still flowing (later packets are arriving), so the network isn't badly congested. Fast Recovery (Reno) uses that: halve cwnd instead of collapsing to 1.

  • CUBIC: default in Linux/Windows/macOS. Window grows as a cubic function of time since last loss; good on high-bandwidth, long-delay paths.
  • BBR (Google): models bottleneck bandwidth and RTT instead of reacting to loss.
  • ECN: routers mark packets (instead of dropping) when queues build; receiver echoes ECE, sender reduces cwnd and sets CWR.

11.7The whole algorithm as one flow

Classic interview question

Why does TCP reduce its sending rate when packet loss occurs? Because loss usually means router queues are overflowing (congestion). Reducing cwnd lowers the traffic injected into the network so queues can drain; otherwise everyone keeps retransmitting and the network collapses (congestion collapse).

11.8Traffic shaping: leaky bucket vs token bucket + Added

A classic GATE/placement question. Congestion control is the sender reacting to the network; traffic shaping is a router or host enforcing a rate.

Leaky bucket

  • Packets enter a bucket (queue) at any rate
  • They leave at a constant rate, like water dripping from a hole
  • Bucket full → packets are dropped
  • Smooths bursts completely; output is rigid

Token bucket

  • Tokens are added at rate r up to capacity C
  • Sending a packet (or byte) consumes a token
  • Allows bursts up to C when tokens have built up, while the long-run rate stays r
  • Used for API rate limiting and QoS policing
Token bucket burst lengthMax burst time S = C / (M − r)

C = bucket capacity (bytes), r = token rate, M = maximum output (link) rate. Example: C = 250 KB, r = 2 MB/s, M = 25 MB/s → S = 250 / 23,000 s ≈ 10.9 ms at full speed.

Variables

  • cwnd → network, rwnd → receiver
  • Effective = min(cwnd, rwnd)
  • ssthresh = switch point

Phases

  • Slow Start → exponential (×2 per RTT)
  • CA → linear (+1 MSS per RTT)
  • AIMD → sawtooth, fairness

Loss reactions

  • 3 dup ACKs → Fast Retransmit
  • Timeout → cwnd = 1, Slow Start (both)
  • Tahoe: 3 dup → 1 MSS
  • Reno: 3 dup → half + Fast Recovery

Finishing the TCP lifecycle: establishment → data transfer → termination.

12.1Why 4 steps?

TCP is full-duplex: each direction is closed independently. The client can say "I'm finished sending" while the server still has data to send. So the server ACKs the client's FIN, keeps sending, and sends its own FIN later.

12.2Step by step

StepDirectionFieldsMeaning
1. FINClient → ServerFIN=1, Seq=x"I have no more data to send."
2. ACKServer → ClientAck=x+1"Got your FIN." Server may still send data.
3. FINServer → ClientFIN=1, Seq=y"I'm also finished sending."
4. ACKClient → ServerAck=y+1Closed (client waits in TIME_WAIT).

FIN consumes one sequence number, just like SYN: FIN Seq = 5000 → ACK = 5001.

+ Added If the server has nothing left to send, steps 2 and 3 are often combined into one FIN+ACK, so you'll see a 3-segment close in packet captures.

Half-close: FIN means "I've finished sending", not "I'll stop receiving". After the client's FIN, the server can still send DATA until it sends its own FIN. Possible because TCP is full-duplex.

12.3TIME_WAIT

After sending the final ACK, the active closer doesn't forget the connection immediately. It enters TIME_WAIT for 2 × MSL (Maximum Segment Lifetime), commonly 60 s total on Linux, though the exact value is implementation-dependent.

Reason 1: delayed old packets

An old segment from this connection may still be in the network. Waiting ensures it dies before a new connection with the same 4-tuple could receive it.

Reason 2: retransmit the final ACK

If the last ACK is lost, the server resends its FIN. A client still in TIME_WAIT can ACK it again instead of answering with RST.

Who enters TIME_WAIT? The endpoint that performs the active close (sends the first FIN), which sends the final ACK. Usually the client, but don't memorise "client always"; it depends on who closes first.

+ Added The passive side goes ESTABLISHED → CLOSE_WAIT (got FIN, waiting for its own app to call close) → LAST_ACK → CLOSED. Lots of sockets stuck in CLOSE_WAIT = an application bug (it never closes). Lots in TIME_WAIT on a busy server = it is the active closer; mitigations include connection reuse (keep-alive) and SO_REUSEADDR.
