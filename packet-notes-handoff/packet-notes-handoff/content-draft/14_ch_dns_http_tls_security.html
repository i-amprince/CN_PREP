The Application layer is where the protocols apps actually use live. Starting with DNS + DHCP, because they explain how a device gets an address and finds a server.

13.1DNS: Domain Name System

Humans prefer google.com; computers communicate using 142.x.x.x. DNS maps domain name → IP address (name resolution). Think of it as the Internet's distributed, hierarchical phonebook.

Transport: DNS commonly uses UDP port 53; it also uses TCP port 53 for zone transfers and for responses too large for UDP (and when the truncation flag is set). Don't say "DNS = UDP only".

+ Added Modern encrypted variants: DoT (DNS over TLS, port 853) and DoH (DNS over HTTPS, 443).

13.2Hierarchy and the resolution walk

  • . (Root) 13 root server identities, hundreds of anycast instances
    • .com TLD server
      • google.com authoritative server → A record
    • .org
    • .in
      • co.in · ac.in
  • Root servers know where the TLD servers are.
  • TLD servers (.com, .org, .in, .edu) point to the authoritative server for the domain.
  • Authoritative server holds the actual records: google.com → IP.
  • Recursive resolver (your ISP's, 8.8.8.8, 1.1.1.1) does the walking for you and caches the answers.

Cache order before any of this: browser cache → OS cache (and hosts file) → resolver cache → hierarchy.

13.3Recursive vs iterative queries

Recursive

Client asks the resolver: "Give me the final answer." The resolver does all the work. (Your laptop → resolver.)

Iterative

The server replies with the best it has: "I don't know, but ask this server." The resolver follows the referrals. (Resolver → root → TLD → authoritative.)

13.4Caching and TTL

If you visited google.com recently, its IP may be cached → cache hit → no lookup. Every DNS record has a TTL in seconds that controls how long it may be cached. Don't confuse it with the IP packet TTL (hop count). + Added Low TTLs allow fast failover/migration; high TTLs reduce load. That is why DNS changes "take time to propagate".

13.6DHCP and DORA

Dynamic Host Configuration Protocol automatically gives a device its network configuration: IP address, subnet mask, default gateway, DNS server (and a lease time). Without it you'd configure these manually.

DHCP uses UDP: server port 67, client port 68.

Why broadcast at first? The client has no IP address yet and doesn't know the DHCP server's IP, so it must shout on the local network (source 0.0.0.0, destination 255.255.255.255).

+ Added · leases and relays
  • Addresses are leased. At T1 = 50% of the lease the client unicasts a renewal REQUEST to the same server; at T2 = 87.5% it broadcasts to any server.
  • The REQUEST is broadcast so other servers that sent OFFERs know they weren't chosen.
  • DHCP relay agent (ip helper) on a router forwards broadcasts to a central DHCP server on another subnet.
  • DHCP RELEASE gives the address back; DECLINE says "that IP is already in use".
  • Attacks: rogue DHCP server (hands out a fake gateway) and DHCP starvation; defence = DHCP snooping on switches.

14.4HTTP is stateless: cookies, sessions, tokens

HTTP itself doesn't remember previous requests; each request is independent. But sites need login, carts and preferences, so we add state on top with cookies, sessions and tokens.

Cookies

Small data the browser stores per domain. Server sends Set-Cookie: sessionId=abc123; the browser sends Cookie: sessionId=abc123 back on later requests to that site. Uses: session tracking, auth state, preferences, carts, analytics.

Session-based authentication

Login: server verifies credentialsServer creates a session (data stored server-side)Sends Session ID in a cookieLater requests: browser sends cookie → server looks up session → identifies user

The cookie may contain only the session ID; the actual data stays on the server.

Cookie

Stored on the client/browser. A transport mechanism.

Session

Server-side state associated with a client (via the session ID).

JWT (JSON Web Token)

header.payload.signature (each Base64URL-encoded), sent as Authorization: Bearer <token>. The server verifies the signature instead of storing a session per client, so it's stateless and scales across servers.

Trap

A JWT is signed, not encrypted by default. Anyone can Base64-decode the payload, so never put secrets in it. + Added Downside: hard to revoke before expiry (use short expiry + refresh tokens, or a deny-list).

Cookie security attributes

  • Secure: only sent over HTTPS.
  • HttpOnly: JavaScript can't read it via document.cookie, which reduces theft by XSS.
  • SameSite (Strict / Lax / None): controls sending on cross-site requests, which mitigates CSRF.
  • + Added Domain / Path / Expires / Max-Age scope and lifetime. No expiry = session cookie (deleted when the browser closes).

14.5HTTP caching + Added

  • Cache-Control: max-age=3600 fresh for an hour; no-cache = revalidate first; no-store = never store; private/public.
  • Validation: server sends ETag or Last-Modified; browser later asks with If-None-Match / If-Modified-Since; if unchanged, server replies 304 Not Modified with no body.
  • Caches exist in the browser, proxies and CDNs.

+ Added · head-of-line blocking (why HTTP/3 exists)

HTTP/1.1: a slow response blocks the ones behind it on that connection, so browsers open ~6 connections per host. HTTP/2 fixes that at the HTTP layer by multiplexing streams, but all streams share one TCP byte stream, so a single lost TCP packet stalls every stream until it's retransmitted (TCP-level HOL blocking). HTTP/3 runs on QUIC, where each stream is delivered independently, so loss on one stream doesn't block others.

Don't say "HTTP/3 is unreliable because it uses UDP": QUIC adds reliability, encryption (TLS 1.3 built in), stream multiplexing and faster setup on top of UDP.

Connects HTTP + cryptography + networking + security. The question: how does HTTPS securely talk to a server?

15.1HTTPS = HTTP + TLS

TLS (Transport Layer Security, successor of SSL) sits between TCP and HTTP and provides:

  • Confidentiality: others can't read the data (encryption).
  • Integrity: modification is detected (MAC / AEAD).
  • Authentication: the client can verify the server's identity (certificates).

+ Added SSL 2.0/3.0 and TLS 1.0/1.1 are deprecated; use TLS 1.2 or 1.3. Which OSI layer? Commonly placed at Presentation (encryption) or "between Transport and Application"; in TCP/IP it's part of the Application layer.

15.2Symmetric vs asymmetric encryption

Symmetric

Same secret key encrypts and decrypts.
  • AES, ChaCha20
  • ✔ Very fast
  • ✘ How do both sides get the same key securely?

Asymmetric

Key pair: public (share freely) + private (keep secret).
  • RSA, ECC
  • ✔ No shared secret needed in advance
  • ✘ Much slower
The core idea
Asymmetric crypto → authenticate the server + establish keys securelySymmetric session keysEncrypt the actual HTTP data (fast)
Interview trap

Q: Does HTTPS encrypt data using the server's public key?
Not the bulk application data. TLS uses public-key mechanisms for authentication and/or key establishment, then symmetric session keys because symmetric encryption is far more efficient.

15.3Certificates and Certificate Authorities

How does your browser know a public key really belongs to google.com? The server presents a digital certificate (X.509) containing: domain identity, public key, validity period, issuer, and the issuer's digital signature.

A Certificate Authority (CA) is a trusted entity that signs certificates. Browsers/OSes ship a list of trusted root CAs.

  • Root CA self-signed, pre-installed in your OS/browser
    • Intermediate CA signed by root
      • Server certificate google.com, signed by intermediate

The browser validates the chain: each signature, validity dates, that the domain matches (SAN), and revocation (OCSP/CRL). Any failure → the red warning page.

15.5Diffie-Hellman and forward secrecy

Client has secret a, server has secret b. They exchange only public values (g^a and g^b), and each independently computes the same shared secret g^(ab). An eavesdropper who sees g^a and g^b can't feasibly compute it.

Modern TLS uses ECDHE (Elliptic Curve Diffie-Hellman Ephemeral). Ephemeral = fresh keys per session. This gives forward secrecy: if the server's long-term private key leaks later, recorded past sessions still can't be decrypted, because their session keys never depended on that key.

15.6Authentication vs encryption, MITM

Certificate

"Who am I talking to?" → authentication.

Session key

"How do we talk securely?" → symmetric encryption.

Man-in-the-Middle: an attacker sits between client and server (Client ↔ Attacker ↔ Server) and impersonates each side. Without authentication, DH alone can be MITM'd (attacker does DH with both). With TLS correctly validated, the attacker can't present a valid certificate for google.com signed by a trusted CA, so validation fails.

+ Added HSTS header forces browsers to use HTTPS for a domain, defeating SSL-stripping attacks. Certificate pinning (in apps) accepts only specific keys.

15.7Hashing and digital signatures

Encryption

Reversible with the right key. Plaintext ↔ ciphertext.

Hashing

One-way, fixed-size digest. SHA-256, SHA-3. Used for integrity, passwords (with salt), signatures. Not reversible.
MessageHash it (SHA-256)Sign the hash with the PRIVATE key → signatureReceiver verifies with the PUBLIC key + recomputed hash

A digital signature gives authentication, integrity and non-repudiation. In certificates, the CA's signature is what makes the certificate trustworthy.

Key direction rules + AddedConfidentiality → encrypt with RECEIVER's public keySignature → sign with SENDER's private key, verify with sender's public keyHMAC → hash + shared secret key = integrity + authenticity (used in TLS records)

If a private key is compromised, an attacker can impersonate that identity, so certificates get revoked.

16.3Proxy, reverse proxy, load balancer, CDN

Forward proxy

Acts for clients. The server sees the proxy, not you. Uses: content filtering, caching, bypassing geo-blocks, corporate egress control.

Reverse proxy

Acts for servers. Clients see one endpoint. Uses: load balancing, TLS termination, caching, compression, hiding backends (Nginx, HAProxy).

Load balancer

  • L4 balances by IP/port (fast, can't see URLs). L7 reads HTTP: route by path/host/cookie, sticky sessions.
  • Algorithms: round robin, weighted round robin, least connections, IP hash (same client → same server), least response time.
  • Health checks remove dead servers from the pool.

CDN (Content Delivery Network)

Caches content at edge servers close to users (often reached via DNS or anycast). Lower latency, less origin load, absorbs DDoS. Examples: Cloudflare, Akamai, CloudFront.
